JOURNEY — HOW TO WRITE THE NEXT ROOM (cheatsheet for AI assistants)
==================================================================

WHAT THIS IS
------------
"Journey" is a branching work of hypertext fiction, published as a fully
static site (GitHub Pages, custom domain in CNAME: journey.victorblackauthor.com).
No build step, no framework, no server code. Plain HTML + CSS + vanilla JS.

The world is an INFINITE square grid of rooms laid over a plane with two axes
of MEANING: north/south is TECHNOLOGY, east/west is MAGIC. The protagonist is an
amnesiac who wakes in the first room and walks from room to room through doors.
The reader IS the protagonist (second person, present tense). The project grows
one room at a time, on demand: when the reader chooses a door that leads
somewhere not yet written, that room gets authored next.

THE TWO COMPANION IDEAS
  - write.txt (this file): how to WRITE a room and keep the world coherent.
  - the existing rooms in rooms/: the canon. Always read the neighbours of the
    room you are about to write before writing it.

FILES
-----
index.html        The cover / threshold. Title + an "enter" door to rooms/0/0.html.
style.css         Shared stylesheet for the cover and every room. Mobile-first.
                  Holds the door-square component and the MEDIEVAL :root palette
                  (the origin's look + the no-JS fallback). It no longer carries
                  era classes — colour is computed from coordinates now.
rooms.js          Shared room script. (1) PALETTE ENGINE: reads the room's (x,y)
                  and interpolates its colours between four corner palettes and a
                  medieval centre, so the look drifts with position automatically.
                  (2) DOOR LOGIC: probes each door's neighbour file; written rooms
                  show "open" (and reveal their name), unwritten ones "undreamt".
                  Included by every room as <script src="../../rooms.js">.
rooms/<x>/<y>.html One self-contained page per room. THIS is what you write. The
                  per-x folders already exist (rooms/-150 .. rooms/150); you only
                  add the <y>.html file inside the right folder.
write.txt         This file.
rooms-map.txt     The room tracker: short how-to-write instructions plus the LAST
                  ROOM written. The next room is derived from that line (see THE
                  FRONTIER). Update its LAST ROOM after writing each room. Not
                  linked by the site.
CNAME             GitHub Pages domain — do not touch.

THE GRID: COORDINATES, FILENAMES, DOORS
---------------------------------------
Every room has integer coordinates x:y. The first room is 0:0. Both axes run
from -150 to +150.
  x grows to the RIGHT (east) = MORE MAGIC; shrinks LEFT (west) = LESS magic.
  y grows UPWARD (north, "forward") = MORE TECH; shrinks DOWN (south) = LESS tech.

Path = "rooms/<x>/<y>.html". The x coordinate is the FOLDER, the y coordinate is
the FILE inside it. Examples:
  0:0  -> rooms/0/0.html        1:0  -> rooms/1/0.html
 -1:0  -> rooms/-1/0.html       0:-1 -> rooms/0/-1.html
The "<x>/<y>" path is the canonical coordinate AND the source of the room's
palette, so both segments must be exactly the integer coordinate — no padding,
no extra dots, no ".html" on the folder. Integers only. The 301 x-folders
(rooms/-150 .. rooms/150) are pre-created; never invent a new folder name.

A room is drawn as a SQUARE with one door centred on each wall. From room (x,y)
the four doors lead to:
  top    (north / "forward") -> (x,   y+1) -> "<x>.<y+1>.html"   MORE TECH
  right  (east)              -> (x+1, y  ) -> "<x+1>.<y>.html"   MORE MAGIC
  bottom (south / "back")    -> (x,   y-1) -> "<x>.<y-1>.html"   LESS TECH
  left   (west)              -> (x-1, y  ) -> "<x-1>.<y>.html"   LESS MAGIC

All four doors are always present in the HTML. rooms.js styles a door as
"undreamt" if its target file does not exist yet — that is normal and expected.

SCALE & FILES (how big this gets, and how to find the next room)
----------------------------------------------------------------
The coordinate space is bounded: -150..+150 on each axis = at most 301 x 301 =
90,601 rooms (~250 MB of HTML at most). That sits comfortably within static
hosting limits, so the whole world can live as plain files in this repo on
GitHub Pages.

Directory: rooms/ is SHARDED — one folder per x value, rooms/<x>/, holding that
column's "<y>.html" files. All 301 x-folders (rooms/-150 .. rooms/150) already
exist; the y.html files are filled in on demand. This keeps every directory well
under GitHub's ~3,000-entry guidance (at most 301 files per folder) and lets the
whole bounded world live as plain files on GitHub Pages.

Because rooms now live TWO levels deep (rooms/<x>/<y>.html):
  - shared assets are referenced as "../../style.css" and "../../rooms.js";
  - a door to a neighbour in the SAME column (north/south, y±1) links to a bare
    "<y>.html"; a door to an ADJACENT column (east/west, x±1) links to
    "../<x±1>/<y>.html";
  - the coordinate is taken from the last two path segments "<x>/<y>" (rooms.js
    parses the path; it also falls back to the ".room-coord" text "X : Y").

What to write next = THE FRONTIER. There is no server to log which doors readers
tried, so the worklist is computed from the files: scan rooms/, and for each room
that exists, note which of its four neighbours (x,y+1 / x,y-1 / x+1,y / x-1,y) do
NOT exist yet. Those missing neighbours are the frontier.

ORDER OF WORK (the standing rule): write rooms ONE AT A TIME, and always take the
unwritten room CLOSEST TO THE ORIGIN first. "Closest" = smallest straight-line
distance from (0,0); break ties clockwise from north (N, NE, E, SE, S, SW, W, NW),
so the next room is never ambiguous. This grows the world as a tight blob around
0:0, so the room you write is always adjacent to one already written — continuity
stays easy and the map never sprouts disconnected islands.

ONE AT A TIME, NOT IN BATCHES (read this twice). Author each room as a COMPLETE
unit, end to end, before touching the next: read its neighbours, write the file,
update the LAST ROOM line in rooms-map.txt — and ONLY THEN move on. Never draft
several rooms' prose in one sweep and save them at the end: if the process is
interrupted you lose the whole unsaved batch, whereas the one-at-a-time loop never
loses more than the single room in progress. It also keeps each room composed with
full attention against its freshly-written neighbours instead of becoming an
assembly line.

"ONE AT A TIME" IS ABOUT THE SAVE RHYTHM, NOT A STOP-AFTER-ONE RULE. When the
request names a number ("write the next 10 rooms"), it means: repeat the one-room
unit above that many times — write a room, save it, update the tracker, then
proceed to the next, looping until you have written that many (or the frontier runs
out). It does NOT mean stop after one. A bare "write the next room" is just the
count = 1 case. Stop early only if the user tells you to, or if something blocks you
(in which case report where you stopped — the saved tracker shows exactly that).

Because rooms are always written in this order, the written rooms form one
unbroken run outward from 0:0 — no full scan or whole-grid map is needed.
rooms-map.txt records only the LAST ROOM written; the next room is simply the next
coordinate in the order above. Write it, save the file, then update the LAST ROOM
line in rooms-map.txt. (If a room is ever added out of order or removed, re-derive
by walking the order from 0:0 outward and taking the first coordinate with no file.)

THE TWO SPECTRA + THE DIAGONAL OF TIME
--------------------------------------
TECH runs along y, MAGIC along x. They are INDEPENDENT dials. Each runs through
the same magnitude bands; |value| 0-10 nascent, 10-40 rising, 40-90 high,
90-150 the pole. Going negative on an axis is not "less" but active LOSS.

  TECH (the y-axis)
    y   90..150   The Tech Pole — post-human: self-building matter, intelligence
                  without flesh, the body wired or shed entirely.
    y   40..90    high tech — electric light, glass, networks, machines that think.
    y   10..40    rising tech — the forge matures into the engine: print, steam.
    y    0..10    nascent tech — hand-tools, the wheel, rushlight. Craft, not industry.
    y    0        THE START band — medieval craft.
    y   -1..-90   pre-tool — fire, flint, hide and bone; the made thing half-dreamt.
    y <= -90      before fire — the body and the dark, older than any tool.

  MAGIC (the x-axis)
    x   90..150   The Magic Pole — reality is consensual: names reshape matter,
                  gods walk, the dead are neighbours.
    x   40..90    high magic — magic as infrastructure: wards, summonings, the
                  dead speak when asked.
    x   10..40    rising magic — working spells, hedge-witches, spirits answer if called.
    x    0..10    nascent magic — omens half-believed; a charm that might be coincidence.
    x    0        THE START band — balance.
    x   -1..-90   disenchantment — magic remembered, then doubted; the charms stop.
    x <= -90      magic dead and forgotten; the Waste, where nothing answers.

THE FOUR CORNERS (where the dials reach their extremes together) — suggested
region names; rename in prose as you like:
    NE (+tech +magic)  THE LUMEN  — magitech: arcane engines, cities of light,
                                    spell and circuit fused. The deep FUTURE.
    NW (+tech -magic)  THE CHROME — the sterile, disenchanted machine; dead neon,
                                    wonder banished, only the engine left.
    SE (-tech +magic)  THE WYLD   — pure myth, the age of wonders, not a gear in sight.
    SW (-tech -magic)  THE WASTE  — ash and ruin, the mundane void; neither spell
                                    nor engine. The primordial deep PAST.
    (0,0)              THE THRESHOLD — medieval, both forces nascent. The balance.

TIME is the SW<->NE DIAGONAL. Toward NE both forces mature together: that reads
as "later", the future. Toward SW is the primordial past. The off-diagonal
corners (NW, SE) are timelines that chose a side — a future that killed magic,
or an eternity that never industrialised.

GRADUAL ALWAYS. A north/south step changes only TECH by one notch (same magic);
an east/west step changes only MAGIC (same tech). And each step is ~1/150 of a
spectrum, so neighbours are nearly identical — let the atmosphere drift by a
hair between rooms, never jump. The palette engine already does this with colour;
your prose should match its restraint.

VOICE & LENGTH
--------------
- Second person, present tense ("You wake...", "You step through...").
- 200-300 words of prose per room. No more.
- Dreamlike, liminal, literary. Concrete sensory detail over abstraction.
- The amnesia is a slow drip: never resolve it quickly. A room may surface ONE
  small fragment (an image, a smell, a name almost remembered) — never a full
  memory, never a tidy explanation.
- End the prose with a quiet beat that turns the reader toward the doors. Do not
  list the doors in prose; the square does that.

CONTINUITY — READ THE NEIGHBOURS FIRST (non-negotiable)
-------------------------------------------------------
Before writing room (x,y):
  1. List its four neighbours and check which files already exist in rooms/.
  2. READ every neighbour that exists.
  3. Honour the shared edge. The door the reader used to ARRIVE here is the same
     physical door, seen from the other side, and it is the OPPOSITE cardinal of
     the one they walked (arrive through a north door -> you entered from the
     south side). If the neighbour's prose said its east door smelled of
     spellwork, then arriving from that side, this room's matching (west) door
     must still owe that scent.
  4. Carry sensory threads across the seam: a sound, a smell, a quality of light,
     a temperature, a recurring object. Continuity is mostly atmosphere.
  5. Plant new hooks under THIS room's unwritten doors that match each door's
     DIRECTION of drift: north hints at more tech, east at more magic, south at
     the more primal, west at the more disenchanted. Whoever writes those
     neighbours later answers your hook.
  6. Keep tech/magic consistent with position (the spectra above).

Room 0:0 already plants these hooks, as the template specimen:
  north door (+tech) -> a faint hum, cold metal-tasting air, a hairline of too-even light
  east door  (+magic) -> torchlight that bends wrong, a bell rung in the mind, old spellwork
  south door (-tech)  -> warm, "almost breathing"; wet earth, older than tools
  west door  (-magic) -> a draught of ash and silence; a gouged SPIRAL, half scratched out
Any neighbour you write must pay off the hook on its shared door.

THEMING IS AUTOMATIC (do not set an era class)
----------------------------------------------
You never choose colours. rooms.js reads the room's coordinates and tints the
page by interpolating between the four corner palettes (Chrome / Lumen / Wyld /
Waste) and the medieval centre. Set ONLY <body class="room"> — nothing more. The
warmth/coldness and hue will already match the room's place in the world; write
prose whose imagery agrees with the colour it will be shown in.

To RETUNE a region's look (not per room — globally), edit the ANCHOR palettes in
the PALETTE ENGINE block at the top of rooms.js. The medieval :root block in
style.css is the origin's palette and the JS-disabled fallback; leave it.

ROOM NAMING & TITLE
-------------------
- Give each room an evocative NAME fitting its tech/magic place (e.g. "The
  Antechamber", "The Pinewood Gate", "The Clockmaker's Landing", "Neon Reliquary").
- The <h1 class="room-name"> text is what neighbouring doors display, and the
  <title> must read exactly:  Room Name — Journey
  (rooms.js reads both; keep the " — Journey" suffix.)

RECURRING MOTIFS (the spine that holds an infinite, branching thing together)
-----------------------------------------------------------------------------
- The SPIRAL: a mark that keeps reappearing in whatever the room is made of —
  chalk here, etched steel in the Chrome, a living vine in the Wyld, a glowing
  glyph in the Lumen, ash-scratch in the Waste. The reader's only thread back to
  themselves.
- The unfinished JOURNEY: the certainty of having been going somewhere.
- The BELL / a distant counting of time, reheard in changed forms (tolling iron,
  a bell rung in the mind, a network ping).
- The almost-remembered NAME.
Reuse at least one motif per room; transform it to fit the room's tech and magic.

CHECKLIST TO ADD A ROOM (x,y)
-----------------------------
[ ] Pick the room: the next coordinate after LAST ROOM in rooms-map.txt — i.e. the
    unwritten room closest to origin (see THE FRONTIER). Write only this ONE room,
    even if more were requested (see ORDER OF WORK: no batching).
[ ] Place the room: read its tech level off y and its magic level off x (the
    spectra above). Know which corner it leans toward.
[ ] Read every existing neighbour file; note the shared-door hook to pay off
    (the arrival door is the OPPOSITE cardinal of the one walked).
[ ] Copy the skeleton; set <title> "Name — Journey", room-coord "x : y",
    room-name, body class="room", and the four door hrefs to the real neighbours:
    north/south stay in this column ("<y+1>.html", "<y-1>.html"); east/west cross
    to the next column ("../<x+1>/<y>.html", "../<x-1>/<y>.html"). Mind negative
    numbers: e.g. from 0:0 the south door is "-1.html", the west door is
    "../-1/0.html".
[ ] Write 200-300 words; pay off the arrival hook; plant new hooks under the
    other doors matching their drift; reuse/transform a motif (the spiral, etc.).
[ ] Do NOT set colours or an era class — the palette is derived from (x,y).
[ ] Save as rooms/<x>/<y>.html (the x-folder already exists). The neighbouring
    rooms' doors light up automatically (rooms.js); nothing else to register.
[ ] Update rooms-map.txt: set its LAST ROOM line to the room you just wrote.
[ ] Save the file and update the tracker BEFORE starting any further room — that
    committed state is what makes the work safe to interrupt. If the request asked
    for more than one room and the count is not yet reached, loop back to the top of
    this checklist for the next coordinate. When the count is done (or the frontier
    runs out, or the user stops you), report the room(s) you wrote and the next
    coordinate in the order.

GOTCHAS
-------
- Keep everything STATIC: no build tools, no npm, no frameworks.
- Rooms live TWO levels deep (rooms/<x>/<y>.html): they reference ../../style.css
  and ../../rooms.js. Same-column doors link to a bare "<y>.html"; cross-column
  doors link to "../<x±1>/<y>.html".
- The path MUST be "rooms/<x>/<y>.html" exactly — x is the folder, y is the file,
  both bare integers, ".html" only on the file. The doors link by coordinate AND
  the palette engine reads it (from the path, falling back to the room-coord
  text). A wrong path or folder mis-colours the room or breaks its doors.
- <body class="room"> only. There are no era-* classes any more.
- Mobile-first: never widen the layout or shrink touch targets; test narrow.
- Use plain ASCII inside any code/command text; typographic entities
  (&mdash; &rsquo; &amp;) are for prose only.
- Do not delete or rename existing rooms — other rooms link to them by file.
