PRODUCE.TXT — Instructions for Claude when generating new story nodes
======================================================================

You are extending a branching dark-fantasy story set in Coulesia, the
Persian-flavoured Khvordemian Empire. Before writing anything, read:

  1. MARK.md         — current progress, last node added, what's next
  2. nodes-map.txt   — beat anchors and reachability map
  3. helpers/ALIGNMENT.md — alignment system and choice design
  4. nodes/<all-parents>.html — every parent whose choice can route a
     player to the node you're writing (see "Reading parents", below)
  5. map/manifest.json (and burgs/, states/, etc.) — for geography

----------------------------------------------------------------------
THE STRUCTURE — ALIGNMENT-KEYED GRID
----------------------------------------------------------------------

Every level past level 1 has up to nine nodes, one per D&D-style
alignment. Node IDs follow the form "<level>-<alignment-code>" where
the code is one of:

  lg ng cg   — Lawful Good, Neutral Good, Chaotic Good
  ln tn cn   — Lawful Neutral, True Neutral, Chaotic Neutral
  le ne ce   — Lawful Evil, Neutral Evil, Chaotic Evil

A LEVEL is anchored to a single STORY BEAT. The nine alignment-nodes
at that level are nine versions of the same beat, each refracted
through the moral grain of one alignment.

The player's current alignment IS their current node. When they make a
choice, story.js applies the deltas, computes the new bucket, and
routes them to the matching node at the next level.

EXCEPTIONS to the 9-per-level rule:
  - Level 0 is a single intro node (0-a) where the alignment is 0/0
    and the player picks a name and gender.
  - Level 1 has gender-distinct nodes (1-m, 1-f). The gender encoding
    has to live somewhere; from level 2 onward prose is gender-agnostic.

NOT every alignment slot at every level is reachable from every prior
state — reachability depends on the deltas of the parent's choices.
Slots that are not first-pass reachable are left vacant for now; they
can be authored later if a re-entry path is added.

----------------------------------------------------------------------
BEAT ANCHORS
----------------------------------------------------------------------

  L1  The man in the ditch          (gender-distinct, two nodes)
  L2  Your hands' first wage        (immediate aftermath of L1)
  L3  The stranger who reads you    (an NPC in/near Sadaiziche
                                     reflects who you've become)
  L4  The second man in the ditch   (repeat moral test)
  L5  A name from before            (first recognition of your
                                     pre-amnesia self)
  L6+ TBD

When you start a new level, decide its beat anchor first and write it
into MARK.md. Every alignment-node at that level then dramatises that
beat through its alignment's lens — same physical situation, nine
moral colourings.

----------------------------------------------------------------------
ROUTING
----------------------------------------------------------------------

Each choice button declares only two data attributes:

  data-law="<integer>"     positive lawful, negative chaotic
  data-good="<integer>"    positive good, negative evil

There is NO data-next. story.js (in assets/story.js) applies the
deltas to the player's state, computes the alignment-code with
threshold T=2:

  law  ≥  2 → "l"     good ≥  2 → "g"
  law  ≤ -2 → "c"     good ≤ -2 → "e"
  otherwise → "n"     (and if both are "n" the code is "tn")

…and routes the player to "<currentLevel+1>-<code>.html".

----------------------------------------------------------------------
PARENT-LEVEL COVERAGE
----------------------------------------------------------------------

When you author a new level N, every destination reachable from any
choice at level N-1 must have a corresponding node at level N. Before
closing the pass:

  1. List every choice at every level-(N-1) node.
  2. Compute each choice's destination bucket from a realistic
     starting state (consider all reachable predecessor states).
  3. Confirm each destination exists at nodes/<N>-<bucket>.html.

If a parent choice routes to a bucket you have not authored, either
(a) author the missing child in the same pass, or (b) change the
parent's choice deltas so the choice no longer routes to a vacant
bucket. Do not leave a 404 reachable from a previous level.

This rule does NOT require every alignment slot at level N to exist —
only the slots any level-(N-1) choice can reach.

----------------------------------------------------------------------
WHAT EACH NODE IS
----------------------------------------------------------------------

  - One HTML file at nodes/<level>-<alignment>.html
  - 500–1000 words of body, aim ~700. Body = inside <div class="story">.
  - Exactly 3 choices, each a <button class="choice"> with data-law
    and data-good only. No data-next.
  - Choices must sample three different parts of the alignment grid
    (see helpers/ALIGNMENT.md). Do NOT write three nearly-identical
    choices.
  - Script tag at the bottom: <script>Story.bootNode("<id>");</script>

CHOICE DELTAS
  Typical magnitude ±1 to ±3 per axis. Reserve ±4 for definitive
  moments. Reflect the FLAVOUR of the choice, not its eventual
  consequence — a player who helps a heretic gets +good even if the
  helping later kills them.

  Before committing deltas, mentally compute where they land the
  player from a realistic starting state. If two choices route into
  the same bucket, it should be intentional (two roads to the same
  moral place); usually you want three distinct destinations.

----------------------------------------------------------------------
READING PARENTS
----------------------------------------------------------------------

Before writing a node at level N, identify ALL nodes at level N-1
whose choices can route a player into your node's bucket. Read each.
Your opening lines must read naturally for arrivals from any of them.

Practically:
  - Do not name a specific prior decision in the opening.
  - Open on the BEAT (the universal physical situation at this level),
    refracted through this alignment's grain.
  - If different parents leave the player in different physical
    states (e.g. wounded man alive vs. dead; player carrying loot vs.
    not), either keep the opening vague enough to accommodate both,
    OR write a one-paragraph framing that resolves which state the
    player arrived in (preferably by reference to alignment, not by
    naming the parent).

----------------------------------------------------------------------
PROSE STANDARDS
----------------------------------------------------------------------

GENDER
  state.gender is "male" or "female" (set at 0-a). From level 2
  onward, prose is gender-agnostic. If a passing line of dialogue
  needs to gender-address the player, write inclusively or use
  ambiguous Khvordemian forms ("traveller", "friend").

NAME
  state.name is set at 0-a. Use sparingly — when an NPC addresses
  the player, or when stylistically necessary. Never assume the
  spelling matches a specific culture.

WORLD AND GEOGRAPHY
  - Khvordemian Empire (state 3 in map/states/index.json, Persian
    culture). Persian Church + Old Vabumism + persecuted Mardesran
    Schism.
  - Anchor scenes in real burgs and routes from the map/ folder.
  - Distances in farsang (Persian league, ~6 km). One day's walk for
    a healthy traveller is ~6 farsang.

TONE
  Dark fantasy. Patient prose. Real physical sensation. Sparse magic
  — when magic surfaces, it should feel old and uncomfortable, not
  bright. The player is amnesiac; flashes of muscle memory are
  welcome but should not collapse into revealing the past too early.
  No emojis, no contemporary slang, no winking narration.

FILES TO UPDATE AFTER EACH GENERATION PASS
----------------------------------------------------------------------

  - nodes-map.txt: add new node IDs, update reachability per parent.
  - MARK.md:
      * update "Last node added" with date and id
      * move newly-written nodes into "Nodes that exist"
      * regenerate the "Next to generate" table for children of the
        nodes you just wrote
      * record any new lore in "Open setting notes"
  - This file (produce.txt) only if a rule changes.
