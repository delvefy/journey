PRODUCE-NEXT-ARTICLE — INSTRUCTIONS FOR CLAUDE
================================================

WHEN THE USER SAYS "produce next N articles":
  Run the PROCEDURE below N times, STRICTLY SEQUENTIALLY. Each iteration must
  be fully completed and committed to disk before the next one begins.

  "Fully completed" means: re-read state.json, write the article file, write
  the seed's counter.json, and write state.json — in that order, for that
  one person — before you so much as think about the next iteration. Do NOT
  batch: do not write several article files in parallel, do not defer
  counter.json updates to the end, do not pre-compute the whole chain in
  your head and then dump it. The candidate-selection in step 6 depends on
  the CURRENT contents of the seed's counter.json, which only become correct
  after the previous iteration has finished writing it.

  Concretely, for N=7 the sequence is:
    iter 1: read state → write article → write counter → write state
    iter 2: read state → write article → write counter → write state
    ...
    iter 7: read state → write article → write counter → write state

  Rationale: if something fails mid-batch, every article completed so far is
  still on disk and state.json points at exactly the next one to write, so the
  user can resume by saying "produce next" again. Batching breaks this
  invariant and tends to drift from the procedure's actual ranking logic.

PROJECT LAYOUT
--------------
  /index.html                              seeds list + per-road table (SPA)
  /style.css                               shared styles, mobile-friendly
  /seeds.json                              [{ "name": "...", "slug": "..." }, ...]
                                           the master list of roads (seeds).
                                           One entry per road.
  /state.json                              { "current_seed": "<slug>|null",
                                             "seeds": {
                                               "<seed-slug>": {
                                                 "next_name": "...",
                                                 "next_slug": "...",
                                                 "complete": false
                                               }, ...
                                             } }
                                           current_seed names which road the
                                           producer is walking right now.
                                           seeds[<slug>] is that road's
                                           progression state. complete=true
                                           when the road hits the 1000 cap.
  /articles/<seed-slug>/                   one folder per road, named after
                                           the seed person's slug.
  /articles/<seed-slug>/counter.json       [{ "name", "slug", "count",
                                              "order" }, ...] scoped to this
                                           road only.
  /articles/<seed-slug>/<slug>.html        one file per person on this road.
                                           The seed person is always the
                                           first article (order=1) in their
                                           own folder.
  /road.py                                 helper that performs the JSON
                                           bookkeeping (see HELPER SCRIPT).
  /produce.txt                             this file

HELPER SCRIPT (road.py)
-----------------------
  road.py owns the MECHANICAL JSON mutations only. It never invents history:
  the article prose, the neighbour shortlist (step 5), the fame ranking
  (step 6) and the choice of CANDIDATE stay with you. You do the thinking and
  write the .html; the script applies your decisions to counter.json and
  state.json atomically, in the project's exact format (2-space indent, raw
  UTF-8, trailing newline), and prints a confirmation so you can verify.

  Run from anywhere; it locates the repo from its own path.

    python3 road.py status [--seed SLUG]
        Procedure step 1. Prints current_seed, the next target, whether that
        target's article file exists yet, road length vs the 1000 cap, and
        the current top-count entries. Run this at the START of every
        iteration to re-read state.

    python3 road.py advance --next "Name" slug [--incr slug ...] [--dry-run]
        Does steps 2, 4, 8 and 9 in one atomic move, AFTER you have written
        the current target's article .html:
          - cap check: at 1000 entries it refuses to append, marks the seed
            complete, clears current_seed, and stops (so step 2 is automatic).
          - appends the CURRENT target (whatever state points at) to
            counter.json with count=1, order=max(order)+1.
          - increments count by 1 for each --incr slug (your step-6 in-MEM
            neighbours that ranked above the candidate); errors loudly if a
            slug is not already in MEM, so a typo can't pass silently.
          - repoints state.seeds[seed].next_* at the CANDIDATE (--next).
        It REFUSES unless articles/<seed>/<target-slug>.html already exists,
        which enforces the write-article-before-bookkeeping ordering for you.
        Use --dry-run to print the plan (append + increments + new pointer)
        and verify your ranking BEFORE committing anything.

    python3 road.py start-seed --name "Name" --slug slug
        The STARTING A NEW SEED flow end-to-end: appends to seeds.json,
        creates articles/<slug>/ and an empty counter.json, sets
        current_seed, and seeds the state entry. Then write article #1.

    python3 road.py finish [--seed SLUG]
        Manual escape hatch to mark a road complete and clear current_seed
        (advance already does this at the cap).

  Typical iteration with the helper:
    1. python3 road.py status                 # see the target
    2. write articles/<seed>/<target-slug>.html (prose + next-link)
    3. (optional) road.py advance --next ... --incr ... --dry-run  # check
    4. python3 road.py advance --next "Cand" cand-slug --incr s1 s2 ...
  The strictly-sequential rule still holds: finish one person's article +
  advance before touching the next.

PER-ROAD CAP
------------
  Each road is capped at 1000 articles. If the current seed's counter.json
  already has 1000 entries when you start an iteration, STOP. Mark
  state.seeds[<slug>].complete = true, clear state.current_seed (set to null),
  write state.json, and tell the user the road is finished and to pick a new
  seed. Do NOT write a 1001st article. (road.py advance does all of this
  automatically when it sees the road is at the cap — it refuses to append.)

SLUG RULES
----------
  lowercase, ASCII only, spaces -> hyphens, strip punctuation.
  Examples:
    "Jesus Christ"          -> "jesus-christ"
    "Joseph of Arimathea"   -> "joseph-of-arimathea"
    "Eleanor of Aquitaine"  -> "eleanor-of-aquitaine"
    "Charlemagne"           -> "charlemagne"

STARTING A NEW SEED
-------------------
  If state.current_seed is null (no road in progress), the user must pick the
  starting person for a new road. Once picked:
    1. Append { name, slug } to seeds.json.
    2. Create the folder articles/<slug>/ if it does not exist.
    3. Create articles/<slug>/counter.json as [] (empty list).
    4. Set state.current_seed = <slug>.
    5. Set state.seeds[<slug>] = { next_name: <picked name>,
                                   next_slug: <picked slug>,
                                   complete: false }.
    6. Write state.json.
  Steps 1-6 above are done for you by:  python3 road.py start-seed
  --name "<picked name>" --slug "<picked slug>"
  Then run the PROCEDURE. The first iteration will write the seed person's
  own article as article #1 on this road.

PROCEDURE (one article)
-----------------------
1. Read state.json. Let SEED = state.current_seed. If SEED is null, stop and
   ask the user to pick a new starting person (see STARTING A NEW SEED).
   Let TARGET = { next_name: state.seeds[SEED].next_name,
                  next_slug: state.seeds[SEED].next_slug }.
   If state.seeds[SEED].complete is true, stop and tell the user this road
   is finished.

2. Read articles/<SEED>/counter.json into MEM.
   If MEM.length >= 1000, stop: mark state.seeds[SEED].complete = true,
   set state.current_seed = null, write state.json, and tell the user the
   road is finished and to pick a new seed. Do NOT continue.

3. Write articles/<SEED>/<TARGET.next_slug>.html using the ARTICLE TEMPLATE
   below. The body must be about 300 words covering the most important
   deeds of TARGET.next_name's life: origins, formative events, principal
   achievements, conflicts and turning points, legacy. Plain prose,
   paragraphs, no headings inside the article body. Do NOT invent facts —
   if uncertain, omit. Expand to up to 500 words ONLY if 300 cannot do the
   life justice (e.g., a figure with many distinct, indispensable episodes).
   Default is 300; 500 is the ceiling, not a target. Leave the "next link"
   pointing to a placeholder you will fill in step 7.

4. Ensure TARGET is in MEM:
   - If MEM already has an entry with slug == TARGET.next_slug, leave count
     and order alone (this should not normally happen, since TARGET was a
     "new" pick last round — UNLESS this is the seed person on the first
     iteration of the road; in that case, append per the rule below).
   - Otherwise append { name: TARGET.next_name, slug: TARGET.next_slug,
     count: 1, order: 1 + max(existing entries' order, or 0 if MEM was empty) }.

5. List 3-5 real historical persons directly connected to TARGET. The
   connection can be of any kind: family, mentor, pupil, ally, rival,
   contemporary, patron, successor, biographer, antagonist, neighbor.
   You only need to know that the edge exists — you do NOT need to know
   the candidate's wider graph, their other connections, or how famous
   TARGET is in their story. This keeps the rule local and cheap.

   NO CHRONOLOGY FILTER. The connection does NOT have to be a
   contemporary or near-contemporary. Cross-era edges are fully valid
   and must NOT be filtered out, down-weighted, or quietly dropped
   because the two people lived centuries apart, or because picking them
   would "pivot" the road into another period. The road is allowed to
   jump eras; that is a feature, not a bug. Valid long-range edges
   include, for example: an interpreter / commentator / synthesizer and
   the long-dead thinker whose work they built on (Aquinas and
   Aristotle; a Renaissance humanist and Cicero), a descendant and a
   distant ancestor, an emulator and the figure they consciously
   modelled themselves on, a translator and their source author. If such
   a person is a genuine edge of TARGET, they BELONG in the shortlist and
   are then ranked purely on fame like everyone else. The ONLY admission
   gate is historical existence (below) — never era, never recency.

   THREE-BUCKET SWEEP. Build the shortlist by deliberately walking three
   buckets, not by free association — free association collapses to
   family and contemporaries and silently drops the cross-era edges this
   road depends on. For every TARGET, gather candidates from all three:
     1. SIDEWAYS — family, allies, rivals, mentors, pupils, patrons,
        contemporaries.
     2. BACKWARD — whom did TARGET build on, model themselves on,
        translate, or descend from? (the long-dead source, the distant
        ancestor, the thinker whose work they continued)
     3. FORWARD — who built on, emulated, translated, descended from, or
        wrote the history or biography of TARGET? This is the bucket most
        easily forgotten, and skipping it is what strands the road among
        obscure locals. Always ask which famous chronicler made TARGET a
        principal subject: Herodotus, Thucydides, Xenophon, Polybius,
        Cornelius Nepos, Diodorus Siculus, Sallust, Livy, Plutarch,
        Tacitus, Suetonius, Arrian, Josephus, Procopius, Bede, Einhard,
        Vasari, and the like.
     4. Pool all three buckets, then rank in step 6 — blind to era and
        blind to MEM status.

   SALIENCE FILTER. Admit a backward/forward edge only if it is SALIENT:
   TARGET is a major subject of that person's work, or a major influence
   on them — not a passing mention. "Nepos wrote a whole Life of TARGET"
   qualifies; "a historian names TARGET once in passing" does not. This
   honors the cross-era rule without collapsing every road into a handful
   of historians: a famous historian, once written, is merely incremented
   thereafter, so they act as a hub back toward fame, never a sink.

   INCLUDE in-MEM persons in the shortlist. Do NOT subconsciously skip
   them just because they cannot be the new CANDIDATE. Their job in
   step 6 is to absorb a count increment before the road moves on, and
   that is the whole point of the counter. In dense clusters (a famous
   court, a family of explorers, a generation of reformers) most of the
   shortlist will already be in MEM — that is the SIGNAL, not noise. A
   TARGET like Anne Boleyn MUST include Henry VIII and Elizabeth I in
   its shortlist even though both are already written, because they are
   the two most famous people directly tied to her, and the road is
   supposed to record that.

   Hard gate: historical existence — NOT biographical certainty. The
   only question is whether the person really lived; how legendary the
   surviving record of their life is does NOT matter. Admit any
   candidate whom mainstream scholarship accepts as a real human being,
   EVEN IF almost everything later told about them is legend, or the
   works under their name are really a centuries-long accretion. Such
   quasi-historical figures — Aesop, Homer, Pythagoras, Lycurgus,
   Sappho — are fully valid and are then ranked purely on fame like
   anyone else. A legend-encrusted biography is NEVER, by itself,
   grounds to drop someone.

   Drop a candidate ONLY when the figure is essentially fictional:
   gods, demigods, and personifications, or persons known solely from
   myth, romance, or devotional invention whom historians take to have
   probably never lived — King Arthur, the Grail cast, William Tell,
   Robin Hood, dragon-slaying or apocryphal saints. (Saints who really
   existed, such as Francis of Assisi, are fine.) The test is what a
   non-specialist historian would say: "probably a real person, however
   embroidered" -> ADMIT; "probably never existed" -> DROP. When
   genuinely unsure, lean to ADMIT.

   For an admitted figure whose life is mostly legend, build the article
   on whatever historical kernel is attested and mark the rest plainly
   as tradition ("by tradition...", "later legend held..."). The
   no-inventing-facts rule of step 3 still binds: report the legend AS
   legend; never manufacture fresh detail.

   Keep the shortlist mental — do not write it to disk, the article, or
   state.json. Only the final pick is visible anywhere.

6. Rank the shortlist by a single criterion: how famous the candidate is
   in general historical memory, irrespective of their connection to
   TARGET and irrespective of the era in which they lived. Fame is the
   ONLY ranking key — never recency, never era, never chronological
   closeness to TARGET, never a wish to keep the road in one period.
   Use whatever rough sense of public recognition you have:
   appears in standard textbooks, has a Wikipedia article in many
   languages, the kind of name a literate non-specialist might recognize.
   Ties broken by your gut. Do not try to score; just sort.

   Rank EVERY shortlist entry, including in-MEM ones. Do not float
   in-MEM names to the bottom — rank purely by fame, blind to MEM status.

   Then walk the ranked list starting at POSITION 1. For each position,
   in order 1, 2, 3, ...:
   - If that candidate's slug is already in MEM, increment that entry's
     count by 1 and move to the next position.
   - The first considered candidate NOT already in MEM becomes CANDIDATE.
   If the shortlist runs out before a new pick is found, extend it with
   more neighbors of TARGET; do not lower the historical-existence gate.

   Sanity check before exiting: if you chose CANDIDATE at position 1 of
   the ranked list, ask yourself whether ANY in-MEM person could
   reasonably be a direct connection AND rank above the CANDIDATE by
   fame. On dense clusters that is suspicious — a Tudor-court TARGET
   that produces zero increments is almost certainly missing a famous
   in-MEM neighbor (Henry VIII, Elizabeth I, etc.) that should have been
   in step 5's shortlist. Re-check before writing counter.json.

   Second red flag — an OBSCURE candidate. If the CANDIDATE you are about
   to pick is obscure, treat that as a signal that you skipped a famous
   FORWARD edge in step 5's bucket 3 (a biographer, historian, translator,
   emulator, or notable heir). Re-run that bucket before committing: an
   obscure pick is far more often a missed famous chronicler or successor
   than a true dead end. Cross-era escapes are the rule, not the exception.

7. Finalize the article we wrote in step 3: replace the next-link placeholder
   with the road's continuation block. The block is now a SINGLE list,
   <ul class="road-links">, with ONE link per <li>, in this fixed order:

   a. PARENT-LINK (dark yellow) — the FIRST item, pointing BACK to the parent
      of TARGET: the article from which the road arrived here. The parent is
      the in-MEM entry with the HIGHEST order BEFORE TARGET itself was appended
      — equivalently, the article whose own next-link points at TARGET. Wrap
      the <li> with class="parent-link" so the stylesheet renders the link in
      dark yellow (the "where we came from" color).
      OMIT this item ONLY on the seed's first iteration, when MEM is empty and
      TARGET has no parent on this road. (The header's "All the roads lead to"
      link already covers the way back to the index.)

   b. BACK-LINKS (dark red-brown) — one <li class="back-link"> PER in-MEM
      neighbor whose count you incremented in step 6, in the order found (the
      step-6 fame ranking, top to bottom). These are real edges of TARGET whose
      articles already exist on this road, so we surface them to the reader
      instead of letting the increment be invisible. OMIT these items entirely
      if no in-MEM neighbors were incremented.

   c. NEXT-LINK (dark blue) — the LAST item, a <li class="forward-link">
      pointing at CANDIDATE, the new entry just appended in step 4. The target
      file does not need to exist yet — the link is forward-looking.

   One link per <li>; never comma-separate several links into one item. Order
   is ALWAYS parent (yellow) -> back-links (red-brown) -> next (blue). Do NOT
   inline colors on the <a> tags — always rely on the <li> class. Example final
   block with all three kinds present:
     <ul class="road-links">
       <li class="parent-link">The road came from <a href="<PARENT.slug>.html"><PARENT.name></a>.</li>
       <li class="back-link">The road also leads back to <a href="x.html">X</a>.</li>
       <li class="back-link">The road also leads back to <a href="y.html">Y</a>.</li>
       <li class="forward-link">The road continues to <a href="<CANDIDATE.slug>.html"><CANDIDATE.name></a>.</li>
     </ul>

8. Write articles/<SEED>/counter.json (pretty-printed, 2-space indent,
   trailing newline).

9. Update state.json:
   - state.seeds[SEED].next_name = CANDIDATE.name
   - state.seeds[SEED].next_slug = CANDIDATE.slug
   Then write state.json.

   Steps 2 (cap), 4 (append target) and 8-9 (write both JSON files) are all
   performed by a single call once the article .html is written:
     python3 road.py advance --next "CANDIDATE.name" CANDIDATE.slug \
        --incr <each in-MEM neighbour slug from step 6>
   You still do steps 3 (write the article), 5 and 6 (the reasoning) yourself.

10. (No need to touch index.html or seeds.json — index.html reads
    seeds.json + each road's counter.json at load time.)

ARTICLE TEMPLATE (articles/<seed-slug>/<slug>.html)
---------------------------------------------------
<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title><PERSON NAME></title>
<link rel="stylesheet" href="../../style.css">
</head>
<body>
<main class="wrap">
  <header class="site"><a href="../../index.html#<SEED-SLUG>">&larr; All the roads lead to:</a></header>
  <article>
    <h1><PERSON NAME></h1>
    <p class="byline"><LIFESPAN OR ONE-LINE EPITHET></p>

    <p>...paragraph 1...</p>
    <p>...paragraph 2...</p>
    ...
    <p>...final paragraph...</p>

    <!-- Continuation block: a single <ul class="road-links">, one link per <li>,
         in fixed order:
           - parent-link  (dark yellow):    FIRST; omit ONLY on the seed (no parent).
           - back-link    (dark red-brown): one <li> per in-MEM neighbor incremented
                                            in step 6, in step-6 rank order; omit all if none.
           - forward-link (dark blue):      LAST; the new CANDIDATE. -->
    <ul class="road-links">
      <li class="parent-link">The road came from <a href="<PARENT-SLUG>.html"><PARENT NAME></a>.</li>
      <li class="back-link">The road also leads back to <a href="<IN-MEM-SLUG-1>.html"><IN-MEM NAME 1></a>.</li>
      <li class="forward-link">The road continues to <a href="<CANDIDATE-SLUG>.html"><CANDIDATE NAME></a>.</li>
    </ul>
  </article>

</body>
</html>

NOTES
-----
- The count field is the road's popularity metric: how many times this
  person was a top-ranked direct neighbor of a later TARGET but was
  skipped because they were already in MEM. Counts above 1 are the
  expected outcome in dense clusters (Tudor court, Iberian explorers,
  the Habsburg-Valois axis). A road on which every count stays at 1 is
  a sign that step 5/6 were applied lazily — in-MEM neighbors were
  silently excluded from the shortlist rather than ranked and
  incremented.
- Articles within a road link sideways within the same folder, so use
  relative hrefs like "joseph-of-arimathea.html" (no folder prefix).
- Stylesheet is at "../../style.css" because articles live two levels deep
  (articles/<seed-slug>/<slug>.html).
- The back-link points to "../../index.html#<seed-slug>" so the index opens
  directly to that road's table.
- The byline line is one short italic line: dates if known, otherwise a brief
  epithet ("Roman emperor", "Florentine painter").
- Do not put any headings inside the article body — only the H1 title.
- Word count: aim for ~300; expand toward 500 only when 300 cannot do the
  life justice. Never exceed 500.
- Never silently overwrite an existing article file. If the article file
  already exists at step 3, something is wrong — stop and report to the user.
- The seed person is always article #1 on their own road (order=1). The
  seed's own next link points to whichever historical neighbor becomes
  CANDIDATE on the seed's iteration.
- Continuation block coloring: the parent link (class="parent-link") is dark
  yellow, the in-MEM back-links (class="back-link") are dark red-brown, and the
  new-road link (class="forward-link") is dark blue. All three are defined in
  style.css under ul.road-links. Do NOT inline colors on the <a> tags — always
  rely on the <li> class.
- Fixed order inside <ul class="road-links">, one link per <li>: parent
  (yellow) first, then the back-links (red-brown), then the next article (blue)
  last.
- The parent-link is present on every article EXCEPT the seed (article #1),
  which has no parent on its own road — omit it there. The parent is the in-MEM
  entry with the highest order before TARGET was appended (the article whose
  next-link points at TARGET).
- The back-link items are OPTIONAL: omit them when step 6 incremented zero
  in-MEM neighbors (i.e., CANDIDATE was at rank position 1). Never emit an
  empty <li class="back-link"></li>.
