VLAD'S JOURNEY — LESSON PRODUCTION GUIDE (for AI assistants)
============================================================

PURPOSE OF THIS FILE
--------------------
This project used to be a random-topic encyclopedia. It has been repurposed
into a single structured COURSE: a self-taught path into penetration testing
that runs from beginner -> intermediate -> advanced.

This file (produce.txt) is the instruction sheet for ONE recurring task:

  "Produce the next lesson."

When asked to continue the course, read this file, look at the lessons that
already exist, work out what should come next, and write it. meta.txt still
describes the SITE PLUMBING (files, JSON schema, design tokens) and is the
companion to this file — read it too if you touch layout or styling.

If a future request ever conflicts with this file, the human's instruction
wins; otherwise follow this file to the letter so lessons stay consistent.


THE LEARNER (write for this person, always)
-------------------------------------------
There is exactly one student: Vlad. Tailor every lesson to him.

  - Works on a MacBook (macOS). Apple Silicon is the assumption unless a
    lesson says otherwise. Every command, install step and tool choice must
    work on macOS. Where the "real" tool is Linux-only (much of the trade is),
    say so and give the mac path: Homebrew, Docker Desktop, or a Kali/Linux
    VM under UTM (Apple Silicon) / VMware Fusion. Never hand him a bare
    apt-get and walk away.
  - QA engineer, 5 years. He already understands: software, the SDLC, the
    terminal, reading logs, writing reproducible bug reports, test cases,
    severity/priority, CI, HTTP basics, maybe some scripting (bash/python)
    and SQL. LEVERAGE THIS. The strongest hook in the whole course is the
    QA -> security bridge: a pentest finding IS a bug report with an exploit
    and an impact statement; recon IS exploratory testing; a repro is a repro.
    Use that analogy whenever it genuinely fits.
  - New to offensive security specifically. Do not assume he knows attacker
    jargon, networking internals beyond the basics, or any tool. Define terms
    on first use. Do not condescend — he is technical, just new to THIS.
  - Comfortable being hands-on. He learns by doing. Every lesson must give
    him something to actually run on his Mac, safely and legally.

Voice toward him: second person ("you"), direct, practical, calm. The site's
encyclopedia chrome stays, but lesson PROSE is a knowledgeable mentor talking
to one student — not a third-person reference entry. (This is the one place
the course departs from meta.txt's "encyclopedia voice".)


THE CURRICULUM ARC (where the course is going)
----------------------------------------------
Three levels. Each lesson declares its level. Don't sprint — let skills
compound. This is a SKETCH, not a contract: adapt to what previous lessons
actually covered, and don't be afraid to insert a lesson the arc didn't name
if the student needs it.

BEGINNER (foundations + a working lab + first real techniques)
  - What pentesting is, ethics & law, the methodology, the QA bridge   (L1)
  - Building the macOS lab: Kali in UTM, vulnerable targets, networking
  - Networking & protocols for hackers (TCP/IP, ports, DNS, HTTP) refresher
  - Linux & the shell for offense; staying organised, note-taking
  - Reconnaissance: passive OSINT, then active
  - Scanning & enumeration with Nmap (deep)
  - Service enumeration (SMB, SSH, web, etc.)
  - Intro to web: how the web works as an attacker sees it

INTERMEDIATE (exploitation across the main domains)
  - Vulnerability analysis & searching for exploits
  - Web app testing with Burp Suite; the OWASP Top 10, hands-on
    (injection, broken auth, XSS, IDOR/access control, SSRF, etc.)
  - Exploitation & Metasploit; manual vs framework
  - Password attacks, hashing, cracking (Hydra, John, Hashcat)
  - Post-exploitation: privilege escalation (Linux & Windows), pivoting
  - Active Directory basics
  - Wireless, and an intro to cloud (AWS/Azure) attack surface

ADVANCED (depth, evasion, specialisation, the craft)
  - Advanced AD attacks, lateral movement, persistence
  - Evasion, AV/EDR awareness, OPSEC for red teams
  - Custom exploitation, basic binary exploitation / fuzzing intro
  - C2 frameworks and adversary emulation (MITRE ATT&CK)
  - Cloud & container exploitation in depth
  - Reporting like a pro, retesting, and the consultant's craft
  - Certification & career paths (OSCP, PNPT, etc.), building a home lab,
    next steps for a QA-turned-pentester

Always finish a lesson with a concrete "Coming up next" that names the most
likely next lesson, so the thread is easy to pick up.


HOW TO PRODUCE THE NEXT LESSON (the procedure — follow in order)
----------------------------------------------------------------
1. READ db/articles.json. Each lesson object has a `lesson` integer and a
   `level`. Find the highest `lesson` number — that is the last lesson.
   (If only Lesson 1 exists, the next is Lesson 2, and so on.)

2. READ the last lesson's HTML file (articles/<slug>.html), and skim one or
   two before it. You must know: what was just taught, what the "Coming up
   next" section promised, which tools are already installed in the lab, and
   what the student can already do. Continuity is everything — never
   reintroduce a tool as new if a prior lesson installed it; build on it.

3. DECIDE the topic. Default to whatever the previous lesson's "Coming up
   next" promised. Otherwise pick the next logical step on the arc above.
   Respect level progression: don't jump to advanced exploitation before the
   lab and recon foundations exist. If the human named a topic, use it but
   still place it correctly in the sequence.

4. WRITE the lesson HTML (structure below) into
   articles/lesson-NN-<kebab-topic>.html, NN zero-padded to two digits
   (lesson-02-..., lesson-10-...). The slug = the filename without .html and
   MUST match the JSON `slug`.

5. REGISTER it: append one object to db/articles.json (schema below). The
   front page sorts by `lesson` ascending and picks it up automatically.

6. SANITY CHECK before finishing:
   - JSON still valid (no trailing comma). `slug` == filename.
   - Every command is macOS-correct and every target is one the student is
     allowed to attack (see SAFETY).
   - The lesson opens with what-you'll-learn and closes with takeaways,
     a self-check, and "Coming up next".
   - You did not silently drop the QA bridge, the lab callout, or safety.

Do NOT modify previous lessons except to fix an outright error or to add a
"next" link — the course is an append-only ledger of what was taught.


LESSON STRUCTURE (the shape of every lesson)
--------------------------------------------
A lesson is NOT the encyclopedia's overview/delve shape. It is a teaching
unit. Aim for roughly 1,800-3,500 words of substance (more for big topics,
less for a tight technique lesson) in this order:

  1. TITLE + meta line: "Lesson NN", level, and an honest time estimate
     (e.g. "~30 min + lab"), plus tag links.
  2. "What you'll learn" — a short <ul> of 3-6 concrete outcomes. First
     thing on the page after the meta.
  3. (Optional) "Before you start" — prerequisites / what must already be
     installed from earlier lessons.
  4. THEORY — the concepts, in clear <h2>/<h3> sections. Explain the WHY,
     not just the what. Use the QA bridge where it fits. Diagrams optional
     (the <figure> element exists); ASCII inside <pre> is fine.
  5. HANDS-ON LAB — at least one, ideally the centre of gravity of the
     lesson. Put it in a `.callout.callout-lab`. Give exact macOS commands
     in <pre class="terminal">, the expected output (dimmed with
     <span class="out">), and "what just happened" interpretation. The
     student must be able to copy/paste and succeed.
  6. SAFETY / LEGAL note where the lesson introduces anything offensive —
     a `.callout.callout-caution`. (Lesson 1 covers law/ethics in full;
     later lessons need only a short reminder pointing back to it.)
  7. "Key takeaways" — <h2> + <ul>, the 4-7 things to remember.
  8. "Check your understanding" — <h2> + <ol>, 3-5 questions (optionally a
     short answer note). QA instinct: make him verify his own learning.
  9. "Coming up next" — <h2> + a sentence naming the next lesson.
  10. (Optional) "References & further reading" — <ol class="references">,
      reputable sources, official docs, the legal practice platforms.

Keep lessons self-contained pages, like the articles, but teaching-shaped.

THE DATABASE ENTRY (append to db/articles.json)
-----------------------------------------------
Same array as before, with two course fields added. One object per lesson:

  {
    "slug": "lesson-02-building-your-macos-lab",   // == filename, no .html
    "title": "Lesson 2 — Building Your macOS Pentesting Lab",
    "summary": "One or two sentences; shown in the list and used by search.",
    "tags": ["intermediate", "lab", "kali"],       // include the level as a tag
    "date": "YYYY-MM-DD",                           // the day you write it
    "lesson": 2,                                    // integer; drives ordering
    "level": "beginner"                             // beginner|intermediate|advanced
  }

Notes:
  - `lesson` is the ordering key the front page sorts on (ascending).
  - `level` must be exactly one of: beginner, intermediate, advanced.
  - Put the level as the FIRST tag too, so tag-search by level works, then
    add 1-3 topic tags. Reuse existing tags before inventing new ones
    (check the JSON for the current vocabulary).
  - Title convention: "Lesson NN — Title Case Topic".


SAFETY, LEGALITY & TARGETS (non-negotiable — every lesson)
----------------------------------------------------------
Penetration testing is legal ONLY with explicit authorisation. Unauthorised
access and scanning are crimes (US CFAA, UK Computer Misuse Act, and
equivalents almost everywhere). Every lesson that touches an offensive
technique must keep the student on legal ground. Permitted targets ONLY:

  - His own machines / VMs / containers on his own lab network.
  - Intentionally vulnerable apps he runs himself: OWASP Juice Shop,
    DVWA, Metasploitable, VulnHub images, OWASP WebGoat.
  - Sanctioned online labs: PortSwigger Web Security Academy (free),
    TryHackMe, Hack The Box, PentesterLab, OverTheWire.
  - Explicitly sanctioned internet hosts: scanme.nmap.org (Nmap permits
    light scanning), testphp.vulnweb.com (Acunetix test site).

NEVER instruct him to scan, probe, or attack a system he does not own or
lack written permission to test. No "try it on a site you like". When a
technique is dual-use, frame it for the authorised-engagement / lab context
and say plainly that doing it elsewhere is illegal. Teach reporting and
defence alongside offence — the goal is a better defender, not a criminal.


HOUSE STYLE (lessons)
---------------------
  - Mentor voice, second person, practical. Define jargon on first use.
  - Lead with the why; show, then explain. Prefer one worked example over
    three abstract ones.
  - macOS-correct, copy-pasteable commands. Mark anything destructive.
  - Use the QA bridge sincerely, not as a gimmick.
  - Typographic niceties carry over: &mdash; dashes, &rsquo; apostrophes,
    &ldquo;&rdquo; quotes (but inside <pre>/<code>, use plain ASCII so
    commands copy correctly).
  - Reuse the styled elements: .callout (callout-lab / callout-caution),
    <pre class="terminal" data-label="...">, the .prompt/.out/.comment spans,
    <kbd>, <blockquote>, <figure>, infobox, references. Do NOT introduce new
    colors, fonts, or off-theme "modern app" styling — see meta.txt.

That's the whole job: read the last lesson, write the next one, register it,
keep him safe and on his Mac. Append to the ledger; keep the journey moving.
